# CGO'27 motivation kernel algorithms and tiling

Date: 2026-08-28

This document describes the algorithms implemented by the
`cgo27_motivation` kernels. It distinguishes the full GEMM input shape from
the compute tile, Local Memory staging tile, K chunk, and DTCU pipeline slice.
Those terms are not interchangeable.

## 1. Common operation

Every implemented mode computes the same GEMM:

```text
G = C + A x B
D = epilogue(G)

A: [M, K], row-major, fp16
B: [K, N], column-major, fp16
C: [M, N], row-major, fp32
D: [M, N], row-major, fp32
```

The full input `(M, N, K)` is generally larger than a hardware or CTA tile.
The grid divides M and N across output tiles, while each kernel or engine
loops over K. A tile only equals a full input dimension when a particular
input happens to have that size.

The current target configuration is:

| Parameter | Value |
|---|---:|
| cores | 4 |
| socket size | 1 core/socket (4 socket DTCUs) |
| warps | 16/core |
| threads | 32/warp |
| issue width | 4 warps |
| input/output | fp16/fp32 |
| Local Memory | 64 KiB (`2^16` bytes) |
| L1 | 32 KiB/socket |
| L2 | 1 MiB/cluster |
| `MOTI_WG_KSTEPS` | 1 |
| `MOTI_WG_NCOLS` | 4 |
| `MOTI_PIPE_TILES` | 4 |
| default pipeline consumers | 15 warps/core |

## 2. Tile hierarchy

The implementation uses four different meanings of tile:

1. **TCU/WGMMA compute tile:** one tensor instruction group's output and K
   step.
2. **LMEM staging tile:** the A/B region copied by software or DXA.
3. **A-resident K chunk:** the portion of A that fits in the 64 KiB LMEM in
   modes 5 and 6.
4. **DTCU pipeline slice:** a row range described by one DTCU descriptor and
   exposed as one completion point to the epilogue consumers.

Current sizes are:

| Mode | Output ownership | K step | LMEM staging | Overlap |
|---|---:|---:|---:|---|
| m0 SIMT | one element/thread | 1 | none | none |
| m1 TCU | `16 x 16`/warp | 32 | none | none |
| m2 TCU+DXA | `16 x 16`/warp | 32 | A `16 x 32` + B `16 x 32`, one buffer | none |
| m3 wg+DXA | `64 x 16`/CTA | 16 | 2 x (A `64 x 16` + B `16 x 16`) | DXA/compute |
| m4 wg SW-copy | `64 x 16`/CTA | 16 | same as m3 | no effective overlap |
| m5 wg+Acol | four `64 x 16` tiles/CTA | 16 | A `64 x Kchunk` + two B `16 x 16` | B/compute |
| m6 wg+Acol SB | four `64 x 16` tiles/CTA | 16 | A `64 x Kchunk` + one B `16 x 16` | none |
| m7 DTCU socket | HW `32 x 16 x 16` | HW loop | DTCU SRAM | internal TMA |
| m8 DTCU cluster | selected HW `64 x 32 x 16` | HW loop | DTCU SRAM | internal TMA |
| m14 socket pipe | m7 tiles grouped into row slices | HW loop | DTCU SRAM | TMA + GEMM/epilogue |
| m15 cluster pipe | m8 tiles grouped into row slices | HW loop | DTCU SRAM | TMA + GEMM/epilogue |

Modes 5 and 6 cover 64 output columns per CTA because they loop over four
16-column tiles:

```text
CTA_N = MOTI_WG_NCOLS x WGMMA_tile_N = 4 x 16 = 64
```

This is not generally `N/2`. It equals N for N=64, N/2 for N=128, and N/4
for N=256.

## 3. Epilogue placement

The placement of the epilogue is part of each algorithm:

| Apps | Operation | Placement |
|---|---|---|
| a1 | identity | no extra arithmetic |
| a2--a5 | elementwise ReLU/GELU/residual/scale | fused in m0--m6; standalone in m7/m8; slice consumer in m14/m15 |
| a6 | row softmax | separate whole-row kernel for every mode |
| a9 | column mean broadcast | separate whole-column kernel for every mode |

a6 and a9 cannot be fused into a GEMM output tile because their reductions
cross tile boundaries. Therefore the m14/m15 consumer pipeline does not
overlap these reduction passes with GEMM.

## 4. Mode 0: scalar SIMT

Each thread computes one output element. A warp covers 32 adjacent columns of
one row.

```text
parallel_for each output element (row, col):
    acc = C[row, col]

    for k = 0 .. K-1:
        acc += fp16_to_fp32(A[row, k])
             * fp16_to_fp32(B[k, col])

    D[row, col] = elementwise_epilogue(acc)
```

There is no tensor or staging tile. The only loop local to one output is the
scalar K loop.

## 5. Mode 1: in-core TCU

One warp owns a `16 x 16` output tile. With fp16 inputs, the K step is 32.

```text
parallel_for each output tile (tm, tn), tile = 16 x 16:
    acc = load_C_fragment(C[tm:tm+16, tn:tn+16])

    for k0 = 0 .. K-1 step 32:
        fragA = load_A_fragment(A[tm:tm+16, k0:k0+32])
        fragB = load_B_fragment(B[k0:k0+32, tn:tn+16])
        acc = WMMA(acc, fragA, fragB)

    acc = fused_elementwise_epilogue(acc)
    store_D_fragment(D[tm:tm+16, tn:tn+16], acc)
```

Operands are loaded directly into register fragments. There is no explicit
prefetch buffer or load/compute overlap.

The introductory comment in `kernel_modes/wmma_common.h` currently calls this
a `16 x 16 x 16` tile. That describes the 32-bit-word-side base geometry; the
actual fp16 kernel advances K by 32 and should be documented as
`16 x 16 x 32` for this experiment.

## 6. Mode 2: TCU with single-buffer DXA staging

Mode 2 uses the same `16 x 16 x 32` compute tile as mode 1 but first copies its
operands into LMEM.

```text
parallel_for each 16 x 16 output tile:
    acc = load_C_fragment(...)

    allocate LMEM:
        As = [16, 32]
        Bs = [16, 32]       // B is physically addressed as N x K

    for k0 = 0 .. K-1 step 32:
        transaction_barrier.expect(2)
        DXA_copy_async(A tile k0 -> As)
        DXA_copy_async(B tile k0 -> Bs)
        transaction_barrier.wait()

        fragA = load_fragment(As)
        fragB = load_fragment(Bs)
        acc = WMMA(acc, fragA, fragB)

        barrier.wait()      // protect As/Bs from early overwrite

    fused_epilogue_and_store(acc)
```

The LMEM footprint is:

```text
(16 x 32 + 16 x 32) x 2 bytes = 2 KiB
```

Because there is only one buffer, the schedule is synchronous:

```text
copy(k) -> wait -> compute(k) -> wait -> copy(k+1)
```

DXA is used, but there is no next-tile/compute overlap.

## 7. Mode 3: workgroup WGMMA with DXA double buffering

The issue width fixes a WGMMA CTA at four warps. Each warp owns 16 output rows,
so the CTA owns a `64 x 16` output tile.

```text
per-warp output = 16 x 16
CTA output      = (4 x 16) x 16 = 64 x 16
K step          = 16
```

```text
parallel_for each 64 x 16 CTA output tile:
    allocate stage[2]:
        stage[s].A = [64, 16]
        stage[s].B = [16, 16]

    acc[warp] = 0

    // Pipeline prologue
    if warp == 0:
        DXA_copy_async(A tile k=0 -> stage[0].A)
        DXA_copy_async(B tile k=0 -> stage[0].B)

    current = 0

    for k0 = 0 .. K-1 step 16:
        wait(stage[current] ready)
        next = current XOR 1

        // Start the next transfer before consuming the current stage.
        if k0 + 16 < K and warp == 0:
            DXA_copy_async(A tile k0+16 -> stage[next].A)
            DXA_copy_async(B tile k0+16 -> stage[next].B)

        each warp loads its own 16 x 16 A fragment
        all warps read the shared B tile through an LMEM descriptor
        acc[warp] = WGMMA(acc[warp], A_fragment, B_descriptor)

        current = next

    each warp:
        D_tile = elementwise_epilogue(C_tile + acc[warp])
        store its 16 x 16 D tile
```

The steady state is:

```text
DXA:    load 0 | load 1    | load 2    | ...
WGMMA:         | compute 0 | compute 1 | ...
```

Warp 0 is the asynchronous request issuer but is not producer-only. After
issuing the request, it participates in WGMMA with the other three warps. The
DXA engine performs the concurrent data movement.

LMEM consumption is:

```text
one stage  = (64 x 16 + 16 x 16) x 2 bytes = 2,560 bytes
two stages = 5,120 bytes
```

## 8. Mode 4: workgroup WGMMA with cooperative software copy

Mode 4 is the matched control for mode 3. CTA geometry, WGMMA geometry, stage
count, and LMEM footprint are identical. Only the producer of the LMEM data is
different: all CTA threads copy instead of DXA.

```text
parallel_for each 64 x 16 CTA output tile:
    allocate stage[2] identical to mode 3
    acc[warp] = 0

    cooperative_copy(tile 0 -> stage[0])
    current = 0

    for k0 = 0 .. K-1 step 16:
        barrier(stage[current] ready)
        next = current XOR 1

        if next tile exists:
            all CTA threads cooperatively copy next tile -> stage[next]

        all warps WGMMA-compute the current tile
        current = next

    fused add-C, epilogue, and store
```

Although it alternates two buffers, the same warps perform copy and compute.
Consequently the software copy of the next stage and current WGMMA are serial
inside the CTA; this is not the asynchronous overlap present in mode 3.

## 9. Mode 5: A-resident WGMMA with double-buffered B

Mode 5 keeps 64 rows of A in LMEM and sweeps four adjacent 16-column output
tiles. It owns a logical `64 x 64` output range, but holds only one `64 x 16`
accumulator tile at a time.

### 9.1 Resident path

When the full A block fits in LMEM:

```text
parallel_for each CTA covering 64 rows x 64 columns:
    DXA_copy_async(A[64, 0:K] -> A_LMEM)
    wait(A ready)

    for n = 0 .. 3:
        tile_col = col_base + n x 16
        acc[warp] = 0

        // B-pipeline prologue
        DXA_copy_async(B tile k=0 -> B[0])
        current = 0

        for k0 = 0 .. K-1 step 16:
            wait(B[current] ready)
            next = current XOR 1

            if another K tile exists:
                DXA_copy_async(next B tile -> B[next])

            each warp loads A from the resident A_LMEM block
            acc[warp] = WGMMA(acc[warp], A_fragment, B[current])
            current = next

        fused add-C, epilogue, and store this 64 x 16 output
        barrier_before_reusing_B0_for_the_next_N_tile()
```

The two reuse mechanisms are different:

```text
A: loaded once and reused by four N tiles
B: streamed for every N tile, with B(k+1) overlapping WGMMA(k)
```

### 9.2 Maximum resident K

`2^16` is the LMEM capacity in bytes, not a tile dimension. For fp16 and two B
stages:

```text
LMEM elements       = 65,536 / 2 = 32,768
B elements          = 2 x 16 x 16 = 512
raw K capacity      = floor((32,768 - 512) / 64) = 504
K-step alignment    = 16
maximum K chunk     = floor(504 / 16) x 16 = 496
```

Thus the largest fully resident A block in the current configuration is
`A[64,496]`.

### 9.3 Chunked path for K greater than 496

The host selects a separate kernel entry when K exceeds the LMEM-derived
maximum.

```text
for n = 0 .. 3:
    acc = 0

    for k_base = 0 .. K-1 step 496:
        k_end = min(k_base + 496, K)

        DXA_copy(A[:, k_base:k_end] -> A_LMEM)
        wait(A chunk ready)

        for k = k_base .. k_end-1 step 16:
            prefetch next B into the alternate buffer
            WGMMA the current A/B tile
            accumulate into acc

    fused_epilogue_and_store_current_N_tile(acc)
```

The N loop is outside the K-chunk loop. Therefore A chunks are loaded again for
each N tile in the oversized path. Reordering the loops would require keeping
four partial accumulator tiles live, which is precisely the register-pressure
problem this mode avoids. The chunked path is correct for large K but loses much
of the N-axis A reuse of the fully resident path.

## 10. Mode 6: A-resident WGMMA with single-buffered B

Mode 6 has the same output geometry and A reuse as mode 5, but only one B
buffer.

```text
DXA_copy(A[64, 0:K] -> A_LMEM)
wait(A ready)

for n = 0 .. 3:
    acc = 0

    for k0 = 0 .. K-1 step 16:
        DXA_copy(B tile k0 -> single_B_buffer)
        wait(B ready)

        WGMMA(resident A tile, single B tile)

        barrier_before_overwriting_the_B_buffer()

    fused add-C, epilogue, and store
```

Its B schedule is:

```text
load B(k) -> wait -> compute(k) -> wait -> load B(k+1)
```

Modes 5 and 6 therefore isolate the benefit or cost of B double buffering
without changing A reuse, output geometry, or epilogue placement.

Mode 6 has one rather than two B tiles, but alignment to a 16-element K step
still produces the same maximum K chunk of 496. Its large-K entry uses the same
outer N loop and inner K-chunk loop as mode 5, without B prefetch overlap.

## 11. Mode 7: socket DTCU

With `socket_size=1`, each of the four cores has a reachable socket DTCU. The
GEMM is split into approximately M/4-row bands and the four engines run those
bands concurrently.

```text
parallel_for each socket/core s:
    band = approximately M/4 rows

    descriptor = {
        A = A[band, :],
        B = whole B,
        C = C[band, :],
        D = D[band, :],
        shape = [band_rows, N, K],
        selected internal tile = 32 x 16 x 16,
        TMA overlap = enabled
    }

    publish_and_verify(descriptor)
    retry until socket engine accepts descriptor
    wait until descriptor.done

if the app is elementwise:
    launch standalone_SIMT_epilogue(D)
```

The device kernel has no explicit M/N/K tile loop. It submits a descriptor;
the DTCU engine performs the conceptual loops:

```text
for mt = 0 .. ceil(band_rows / 32)-1:
    for nt = 0 .. ceil(N / 16)-1:
        acc = C tile

        for kt = 0 .. ceil(K / 16)-1:
            TMA-prefetch operands
            MAC the current tile while adjacent movement progresses

        store D tile into the producing socket's L1
```

Ragged trailing M/N/K tiles are clamped by hardware.

## 12. Mode 8: cluster DTCU

There is one cluster DTCU. Each of the four cores submits approximately M/4
rows to the same engine queue.

```text
parallel_for each core c:
    band = approximately M/4 rows

    descriptor = GEMM(band, whole N, whole K)
    descriptor.tile = 64 x 32 x 16

    publish_and_verify(descriptor)
    retry until cluster queue accepts descriptor
    wait until this descriptor.done

if the app is elementwise:
    launch standalone_SIMT_epilogue(D)
```

Four descriptors do not mean four MAC arrays. One engine processes the queued
descriptors. This mode therefore includes descriptor-request, descriptor-wait,
and engine-refill overhead. Its output is placed in L2.

The cluster engine supports runtime tile-N values from 16 through 128 in steps
of 16. The harness currently fixes tile-N at 32, so the measured internal tile
is `64 x 32 x 16`; 128 is the hardware maximum, not the tile used by this
experiment.

## 13. Mode 14: socket DTCU producer/consumer pipeline

Every core divides its own row band into DTCU-tile-aligned slices and assigns
disjoint warp roles:

```text
warp 0       = producer-only
warp 1 .. cw = consumers
default cw   = 15
maximum cw   = 15, because the core has 16 warps
```

### 13.1 Slice size

```text
band_rows = approximately ceil(M / number_of_cores)
socket tile-M = 32
tile_count = ceil(band_rows / 32)
T = min(MOTI_PIPE_TILES=4, tile_count)
```

Each slice contains a whole number of 32-row engine tiles, except for the
hardware-clamped final ragged tile. A slice is therefore not a blind `M/T`
division.

### 13.2 Pipeline algorithm

```text
for each core:
    band = this core's M-row band
    split band into T tile-aligned slices

    producer warp 0, lane 0:
        for t = 0 .. T-1:
            build descriptor(slice[t])
            publish descriptor
            retry until socket engine accepts it
        return

    consumer warps:
        for t = 0 .. T-1:
            if consumer_warp == 0 and lane == 0:
                poll slice[t].done with register-only backoff

            barrier(consumers only)

            for each row assigned to this core in slice[t]:
                all cw x 32 consumer threads split the row's columns
                apply the elementwise epilogue in place
```

The steady state is:

```text
socket DTCU: GEMM slice 0 | GEMM slice 1 | GEMM slice 2 | ...
consumers:                  epi slice 0  | epi slice 1  | ...
```

Mode 14 therefore has two pipeline layers:

1. the engine's internal TMA/compute/store pipeline; and
2. software overlap between GEMM of slice `t+1` and epilogue of slice `t`.

At small M, a core's band may contain only one 32-row tile. Then `T=1`, so no
slice-to-slice overlap exists even though producer/consumer launch overhead is
still paid.

## 14. Mode 15: cluster DTCU producer/consumer pipeline

The cluster has only one engine, so it uses one producer for the whole cluster:

```text
core 0, warp 0, lane 0 = sole producer
participating warps on every core = consumers
```

The whole M range is sliced using the cluster tile-M:

```text
cluster tile-M = 64
tile_count = ceil(M / 64)
T = min(MOTI_PIPE_TILES=4, tile_count)
```

```text
producer on core 0:
    split the whole M range into T slices aligned to 64 rows

    for t = 0 .. T-1:
        build descriptor(slice[t], tile = 64 x 32 x 16)
        publish descriptor
        retry until cluster queue accepts it
    return

on every core:
    select cw consumer warps

    for t = 0 .. T-1:
        one lane on this core polls slice[t].done
        barrier among this core's consumers

        stripe the completed slice's rows across the four cores
        use cw x 32 threads per core to split a selected row's columns
        apply the elementwise epilogue
```

The cluster queue depth is `2 x NUM_CORES = 8`, while the default maximum
number of slices is four. The producer can normally submit every slice up
front.

```text
cluster DTCU: GEMM slice 0 | GEMM slice 1 | GEMM slice 2 | ...
four cores:                  epi slice 0  | epi slice 1  | ...
```

D lands in L2, so all consumers see the same placement. The cost is that DTCU
operand traffic, completion polling, and consumer epilogue traffic contend for
the L2 path. Only one lane per core polls, and polling uses register-only
backoff, to avoid starving the engine with AMOs.

Rows are striped by core rather than by warp. Giving every warp independent
rows creates too many concurrent L2 lines and previously livelocked by starving
the lower-priority engine request path.

## 15. Limits that must not be conflated

| Quantity | Current value | Meaning |
|---|---:|---|
| LMEM capacity | 65,536 bytes | storage, not K or N |
| m5/m6 maximum K chunk | 496 elements | largest aligned resident A depth |
| m5/m6 CTA N coverage | 64 columns | four sequential 16-column outputs |
| socket DTCU tile | `32 x 16 x 16` | fixed internal compute tile |
| cluster DTCU selected tile | `64 x 32 x 16` | tile used by this harness |
| cluster DTCU maximum tile-N | 128 | supported hardware bound |
| software pipeline slices | at most 4 | descriptor completion points |
| consumer warps/core | at most 15 | one producer warp remains disjoint |
| DTCU descriptor M/N/K | at most 65,535 each | descriptor fields are `uint16_t` |

In-core modes additionally require exact divisibility by their grid and tile
geometry. DTCU modes accept ragged trailing tiles and clamp them in hardware.

## 16. Mode status

Modes 9--11 are planned heterogeneous TCU+DTCU modes but are not implemented in
the current kernel set. Modes 12 and 13 are reserved numbering holes. They must
not be presented as measured algorithms.
