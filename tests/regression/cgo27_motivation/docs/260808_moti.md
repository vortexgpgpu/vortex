# No placement wins everywhere

**Two axes, one GEMM harness, four modes that each own part of the grid.**

This document replaces the single-winner framing the earlier figures carried. The question
is not which unit is fastest — it is *which unit is fastest for which work*, and the answer
changes along both axes measured here.

The diagrams are unchanged from `260807_dtcu_figures.html`; only the experiments are new.

**Two placements of the same descriptor engine.** `DTCU_socket` puts one engine in each
socket and writes *D* into that socket's L1; `DTCU_cluster` puts one in the cluster and
writes to L2. With `SOCKET_SIZE = 1` on a four-core cluster that is four engines against
one, so the pair separates *where D lands* from *how many engines the placement buys*.

**Modes 1 and 5 keep the work in the cores** and differ in how much reuse the geometry
gives them: mode 1 loads every fragment through the LSU, mode 5 stages its A rows for the
whole K range into Local Memory once and sweeps four column tiles against them. **Modes 7
and 8 hand the GEMM to an engine**; the core only submits a descriptor and polls.

## The two axes

**Axis 1 — shape, through arithmetic intensity.** For a GEMM,

```
AI = M·N·K / (M·K + N·K + M·N)   →   ~K   as M and N grow
```

so **K decides whether a shape is memory-bound or compute-bound**. Attention's `QK⊤` has
`M = N = seqlen` against `K = head_dim`, and head_dim does not grow when the sequence does —
that family stays memory-bound at every size. A cube where all three grow together becomes
compute-bound. A cubic ladder is therefore a *machine-scaling probe, not a workload*, and is
labelled as one here.

**Axis 2 — the epilogue.** The in-core modes fold an elementwise activation into the
accumulator while it is still in registers. The DTCU is GEMM-only hardware: its descriptor
produces a bare *D*, so the same activation is a **second full launch**. And app 6 (row-wise
softmax) is the case nothing can fuse — a row spans more output tiles than any warp owns, so
the row max and row sum are unknown until every tile is written. Every mode pays an extra
pass there, and the engines pay a third.

**The epilogue is chosen by the preprocessor, one per binary.** `MOTI_APP` selects it at
compile time, so a binary contains exactly one and an app the run does not use cannot
relocate a mode's code in the icache. That matters: carrying two unused epilogue kernels
moved mode 4 by +44.6 %. Each column below is therefore its own build.

## The result

| shape | app 1 — none | app 2 — ReLU | app 3 — GELU | app 6 — softmax |
|---|---|---|---|---|
| 128 × 64 × 32 *(small cube)* | **7** | **7** | **7** | **7** |
| 256 × 256 × 64 *(attention, K = 64)* | **7** | **5** | **7** | **7** |
| 768 × 384 × 192 *(large cube)* | **5** | **5** | **1** | **1** |
| 1024 × 1024 × 64 *(attention, K = 64)* | **7** | **7** | **7** | — |

**Three different modes win, and the epilogue moves the boundary as much as the shape does.**

- **The engine owns the memory-bound end.** At the small cube it takes every app. At
  256 × 256 × 64 — attention-shaped, so memory-bound however large it gets — it takes app 1
  by 2.14× over the in-core TCU.
- **An epilogue narrows or reverses that.** At the same attention shape ReLU costs mode 5
  *nothing* (97,515 → 97,470) and costs the engine **+28.7 %** (87,782 → 112,944), which is
  enough to hand the win to mode 5. The engine pays in memory traffic where the in-core modes
  pay in arithmetic.
- **The compute-bound end belongs to the cores.** At 768 × 384 × 192 mode 5 beats the engine
  by 1.38× on app 1, and with GELU attached plain mode 1 takes it back — three different
  winners in one row of the grid.
- **Softmax is the leveller.** No mode can fuse a row reduction, so the extra pass dominates
  everything: at 128 × 64 × 32 the spread across modes 1/5/7/8 collapses from 4.2× (app 1) to
  1.2× (app 6). When the epilogue cannot be fused, where the GEMM ran stops mattering much.

### What is not here

- **Apps 4, 5, 7 and 8 are not built.** They need an operand the kernel has no pointer for —
  a residual matrix, a per-channel scale, a bias — or int8 inputs, which is a build variant of
  `ITYPE` rather than a runtime app. `MOTI_AUX_ELEM_OFFSET` in `common.h` is the agreed route
  for the first three: the host appends the array to the C buffer and the kernel derives the
  address, so none of them needs a `kernel_arg_t` field.
- **Modes 2, 3 and 4 are measured but not shown.** They are controls — 2 isolates DXA without
  the geometry that makes it pay, 4 isolates the geometry without DXA, 3 is mode 5 without
  A-residency. They belong in the argument, not in a table of candidates.
- **`—` is a run that has not landed**, not a failure. The 1024 × 1024 × 64 row is still
  filling.
- **Roughly a fifth of sweep points in this harness never terminate**, at shapes with no
  discernible pattern, and mode 1 is the only mode that has never done it. Every ratio above
  is drawn from the subset that ran. This is unexplained and tracked separately.
