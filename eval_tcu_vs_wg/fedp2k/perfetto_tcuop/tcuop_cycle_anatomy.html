TCU_OP Cycle Anatomy

app sgemm_tcu_op 128×128×128 fp16→fp32, dense NW=16 NT=32 IW=4 16 MMA_OPs × 32×32×128 tile 81,087 cycles traced = untraced

The engine is busy 80.8% of the time, and while busy it runs at its full rate: one 32-MAC step every cycle, with no bubbles. TCU_OP is sub-optimal for two reasons. Its peak is low: one engine at 32 MACs/cycle, so even a perfect run is slower than WGMMA at IW=4. It also loses 19% to serialized overhead: an all-zero C preload before every tile, compulsory icache misses from fully unrolled code, and tile-0 staging with nothing to overlap it.

The ceiling is the first problem

At IW=4, four TCU blocks are instantiated but only issue block 0 is connected to memory. That engine peaks at 2×16 = 32 MACs per cycle. With zero overhead the 2,097,152 MACs would still need 65,536 cycles, which is already slower than WGMMA with the same block provisioning.

Causes, largest first

  1. ceilingstructural

    One 32-MAC/cycle engine, whatever the issue width

    Only TCU block 0 reaches memory (the other three are tied off in VX_tcu_unit.sv), and the FEOP array is 2×16 by default. That's why TCU_OP is flat across IW and last at IW=4.

    To raise it: connect more engines, or widen the FEOP array. DXA would limit next: its one worker needs about 2,560 cycles to stage each 20 KB tile, which caps throughput at roughly 1.6× today's compute rate.

  2. 4,4965.5%

    C is preloaded serially before every tile, and here C is all zeros

    The engine issues its 32 C requests about one every 9 cycles, 280 cycles in all, and only then starts A/B (VX_tcu_op_core.sv:129: “A requests start only after the ACCU is initialized”). Passing a null C doesn't help: line 776 still issues the reads, redirected to A, and just discards the data.

    Fix: skip the preload when C is null (initialize the accumulator to zero), or let A/B fetch start while C is still loading. On the DXA side, skip staging C when it is known to be zero.

    Implemented and measured. For a dense tile with init set and a null C, the engine now skips the preload, and the first k-set's writes overwrite the accumulator instead of adding to it. With the same kernel binary: 80,839 → 76,350 cycles (−4,489; predicted 16 × 281 = 4,496). Against the original 81,087: −5.8%, 54.9 FLOP/cycle. Operand fetch per tile fell from 291 to 11 cycles. All 6 CI cases and all 7 sparse and dense-control cases pass, and runs with a real C are unchanged at 81,087.

  3. 3,1913.9% + startup

    Compulsory icache misses from fully unrolled per-tile code

    All 38 code lines (0x80000040→0x80000980) are fetched exactly once, about two misses per tile. From tile 5 onward each tile's D write-back evicts older D lines, and refills slow from ≤323 to 650–850 cycles. Every slow refill had 30–51 DRAM write-backs issued during it; every fast one had none. Most misses are hidden behind compute. Three land in the result → next-MMA_OP window and stall the engine, and one more delays kernel exit.

    Fix: keep the tile loop rolled so iterations reuse cached lines, or prefetch the next tile's code while the engine computes.

  4. 4,0485.0%

    Startup puts all of tile 0's staging on the critical path

    Warp 0 finishes its prologue (four compulsory misses) around cycle 1,140, then waits about 2,870 cycles while the single DXA worker stages C → A → B one after another, 830 cycles of it spent on the all-zero C. B0 lands 41 cycles before the first MMA_OP.

  5. 3,5004.3%

    Tiles never overlap

    Drain (137) + handoff (~77) + fetch (291) come to about 506 cycles per tile with no compute. The engine never received an MMA_OP while it was still busy (zero execute-stall events during the kernel), so the next tile's fetch can't hide behind the current tile's drain. Whether the engine can queue a second operation is not yet verified.

DXA staging is not a bottleneck after tile 0. Every transfer finishes at least 1,150 cycles before the tile that needs it fires.

Tooling gaps found along the way. The stock exporter ci/perfetto.py drops the whole TCU_OP engine, because its trace lines carry no instruction UUID. --debug builds don't enable DBG_TRACE_DXA, so DXA is invisible unless you add it by hand. LMEM bank events land on an “unknown” track, and instruction lifetimes are filed under “Global Legacy Events”.
