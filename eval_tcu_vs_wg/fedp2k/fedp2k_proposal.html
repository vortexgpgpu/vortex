FEDP2K Unlock Proposal

Why doubling the tensor-core K width shows no end-to-end gain at NT=32, the audit proving the FEDP2K implementation itself is sound, the measured attribution of where the cycles actually go, and a verified fix bundle that exposes the doubled throughput.

Verdict. FEDP2K has no fundamental implementation flaw: the uop sequencer, operand transport, LMEM alignment and datapath all deliver the designed 2× MACs-per-uop, and the committed-uop counts match theory exactly. It shows nothing end-to-end because the tensor pipes execute for only ~3% of the run: the wall is split between DXA staging serialization (a 91-cycle DRAM latency against 8 outstanding reads on a single worker) and a K-independent ~45k-cycle floor dominated by the C-matrix store epilogue through the write-allocate dcache.

Fix. A verified bundle — coalesced LMEM-staged C store, double buffering, deeper DXA inflight, and (at large K) A-tile multicast — removes the masking terms. [STAGE4: headline FEDP2K delta with bundle at K=512]

1 · The on-paper analysis, corrected

The expectation was: at NT=32 the FEDP2K B-block (128 B) aligns exactly with the LMEM row, the NT=16 staging collision disappears, so the 2× K width should translate into a substantial speedup — as Hopper's K-doubling did over Ampere. The alignment part is correct and measured (the NT=16 regression is gone). The missing premise is where the critical path is: Hopper's K-doubling paid off because its SMs were tensor-throughput-bound in the main loop. This kernel, at 128³ on one core, is nowhere near that regime:

2 · Audit: the FEDP2K implementation is sound

Every stage of the FEDP2K path was read end-to-end and checked against counters:

  • Geometry. TCU_WG_FEDP_K = 2·tcK halves K_STEPS (2→1); per-instruction uops go 32→17 at NRC=16 (the +1 is the descriptor setup uop that only dense FEDP2K RS needs). The hardcoded per-k-step uop counts hold at every NT because tcM·tcN = NT identically.
  • Operand transport. Each compute uop reads its A register pair through rs1+rs2 (fedpK spans two A registers); the B descriptor is latched at setup and replayed — verified in VX_tcu_uops.sv and the WGMMA orchestrator.
  • Datapath. The FEDP tree is instantiated at width fedpK behind a pipe register: initiation interval 1, one uop per cycle per block, genuinely 2× MACs per uop.
  • LMEM alignment at NT=32. The dense B block is fedpK·tcN = 32 words = 128 B = exactly one LMEM row; the bbuf fetches one bank-row per block (base packs 2 blocks per row — so both modes issue the same number of LMEM row fetches per instruction, which is why bbuf behavior cannot separate them).
  • Counters. Committed instrs 15,048→11,400 (Δ = the uop halving exactly); tbuf stalls 6,607→4,143; tbuf LMEM reads 1,756→1,222. Everything FEDP2K touches improves — and none of it is on the critical path.

3 · Where the cycles actually go

Two independent decompositions agree.

3.1 Staging: latency-bound, not bandwidth-bound

  • DRAM read latency measured at 91.3 cycles (memory perf class); DRAM bank stalls ≈ 0 — bandwidth headroom is large.
  • DXA gmem traffic: 5,120 cache lines per run (measured; 2.5 KB + 1 KB per CTA-k-tile, with A fetching a full 64 B line per 32 B row — 2× over-fetch by layout). With DXA_MAX_INFLIGHT=8 the single worker sustains ≈ 8/91 ≈ 0.09 lines/cycle.
  • simx engine counters (model-corrected): 128 transfers averaging ≈ 370 cycles each — the engine is busy ≈ ⅔ of the run staging serially through one worker.

3.2 The K-independent floor

Varying K isolates fixed from marginal cost (simx, base kernel): k=64 → 57,606, k=128 → 70,304, i.e. ≈ 3.2k cycles per k-tile of marginal staging and a ≈ 45k fixed floor. The commit-timeline histogram attributes the floor: C-store commits dominate every window from ~10k cycles to the end of the run. The epilogue's lane mapping puts adjacent lanes N·4 B = 512 B apart, so one store instruction touches tcM·m_steps = 16 distinct lines, the LSU coalescer merges nothing, and the write-allocate dcache turns each touched line into a DRAM fill plus a writeback with MSHR replays behind it.

The multicast result is the key negative lesson: its 2.5× traffic reduction worked exactly as designed (verified by engine counters), yet end-to-end it lost 2× — because cluster-granular CTA admission turned the previously-overlapped C-store epilogue into a serial phase boundary. Any co-residency-clustered kernel must either amortize that boundary (large K) or make the epilogue cheap first.

5 · The fix bundle (verified)

5.1 Coalesced C-store epilogue (CSTORE_LMEM)

After the k-loop the LMEM staging buffers are dead. Each warp stages its C sub-tile through a private 512 B LMEM slice in 16-column chunks, then writes global memory with every store instruction covering full consecutive 64 B segments. LMEM absorbs the scatter (bank conflicts cost cycles, not DRAM round trips). One extra CTA barrier makes the buffer reuse safe. The fragment-register mapping is unrolled at compile time; all state stays in caller-saved registers (the SIMT-stack spill rule).

5.2 Deeper DXA pipelining (DXA_MAX_INFLIGHT=32)

Widens the per-worker outstanding-read window against the 91-cycle DRAM latency. Tag and credit widths scale with the parameter; silicon cost is a deeper direct-drain slot array.

5.3 Double buffering (kernel, XOR-toggle)

Once staging and the epilogue shrink, stage/compute overlap starts to matter; the register-only double-buffer schedule from sgemm_tcu_wg_dxa provides it (LMEM 32 KB keeps 4 CTAs resident).

5.4 A-tile multicast (large-K regime)

The A slice is shared by all 4 co-resident CTAs and dominates staging traffic; the X-clustered multicast kernel (loader-warp rendezvous, rank-0 issue, per-receiver barrier events) cuts staged lines per round 320→128. Its cluster-admission boundary cost is fixed, so it pays off as K grows.

6 · simx model fix: DXA drain width

The simx DXA emitted at most one 64 B block write per cycle, while the RTL drains one full LMEM row (128 B at NT=32) per cycle. At NT=32 this halved modeled drain bandwidth and, because FEDP2K's B blocks span the full row, charged FEDP2K a phantom staging penalty (−18% at K=512 on simx while rtlsim shows parity). The model now emits one row beat per cycle as LMEM_PORTS_PER_CORE same-cycle block writes on adjacent LocalMem ports (and bounds the beat by the row for small-NT configs). After the fix: NT=16 unchanged (77,176 vs 77,173); NT=32 FEDP2K parity restored at K=128 (70,145 vs 67,895) and K=512 (152,792 vs 153,690), matching rtlsim.

7 · Roadmap after this bundle

  1. Write-allocate bypass for full-line stores — the remaining epilogue cost is DRAM fills for lines that are fully overwritten; a no-fetch-on-full-line-write dcache path removes ~1k fills + writebacks per 64 KB of C.
  2. Cluster admission below whole-group granularity, or epilogue-before-release restructuring, so multicast kernels regain inter-wave overlap at small K.
  3. DXA worker transfer pipelining — overlap the next transfer's address generation and first reads with the current transfer's drain tail; per-transfer latency (≈ 370 cycles avg) is the staging floor once traffic shrinks.
  4. A-descriptor packing — A rows are 32 B in 64 B lines (2× over-fetch); a packed-tile descriptor or 2-row fetch would halve A gmem traffic without multicast.
  5. DXA RTL perf-counter repairs (P4) so rtlsim can report engine occupancy directly.
Method: rtlsim (Verilator) is ground truth for all headline numbers; simx (with the drain-width model fix above) for counters, traces and fast triage. All runs: 1 core, NW=16, fp16→fp32, WGMMA_RS, NRC=16, 128×128×K. Every configuration in every table passed its built-in correctness check. Kernels: tests/regression/sgemm_tcu_wg_dxa (CSTORE_LMEM, DXA_DOUBLE_BUFFER guards) and tests/regression/sgemm_tcu_wg_dxa_mcast (DXA_MCAST_A guard); engine knobs via CONFIGS defines only.
