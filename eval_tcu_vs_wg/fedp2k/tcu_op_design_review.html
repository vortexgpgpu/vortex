TCU_OP Architecture Design Review

Vortex vortex_spg, branch tcu_op · reviewed 2026-09-17 · covers hw/rtl/tcu/VX_tcu_op_core.sv (1,635 loc), VX_tcu_feop.sv, VX_tcu_feop_accu.sv, VX_tcu_pkg.sv, VX_tcu_unit.sv, tests/regression/sgemm_tcu_op/{kernel,main}.cpp, plus the core-side integration (decode, wctl, mem_unit, local_mem)

Verdict. TCU_OP (published as SparseWeaver) is a sparsity-first decoupled tensor engine whose architecture is sound and whose design decisions — outer-product FEOP datapath, bitmap-driven dual-side sparsity with hardware step-skipping, direct shared-memory operands, on-TCU accumulation, asynchronous tx-barrier completion — hold up under review and are worth keeping. The implementation had never been brought up against the modern Vortex tree and was riddled with defects: this session found and fixed 11 functional bugs (4 of them in shared core RTL or its contracts, latent for other clients) to take the model from "does not launch" to passing numerical verification at 1, 2, 4 and 16 output tiles.

Two caveats on that claim. First, every passing run was a --debug=2 build; the --perf and plain builds deadlock reproducibly at 128³ (and still do with the stall timeout raised to 2M cycles), so a correctness difference remains between debug and non-debug builds and the model is not yet verified in a normal build (§5.1). Second, the 161,988-cycle / 25.9 FLOP-per-cycle figure below is from that debug build and should be treated as provisional.

Beyond correctness, the RTL carries real synthesis and efficiency flaws — a runtime 32-bit divide/modulo in the per-cycle issue path, 4× area replication with one usable instance, half-width memory port utilization, and zero inter-op pipelining. But note what is not a flaw: the crossbar, input queues, sorters and dynamic step counts exist to convert unstructured dual-side sparsity into skipped work, and judging them against dense GEMM (where the bank mapping is static and conflict-free) misreads the design's purpose. The dense corner tops out at 64 FLOP/cycle at the 2×16 geometry — parity with the measured WGMMA+DXA pipeline — and the architecture's actual value proposition lies in the sparse regime plus the area/throughput scaling axis that its barely-utilized LMEM port can still feed.
Source note. This review was written from the RTL and kernel sources, then cross-checked against the design paper (SparseWeaver: Co-Design Tensor Core and Microarchitectural Adaptations for Unstructured Sparsity in RISC-V GPUs, DATE 2027 submission, custom/DATE_2027___SPARSE_TCU.pdf). The paper's architecture, dataflow and kernel sections match the implementation closely and are used here for intent and naming; its evaluation section describes an older, discontinued Vortex 2.0 implementation and is therefore not used as a performance reference.

1. Architecture overview & motivation

TCU_OP replaces the WMMA/WGMMA "instruction-per-µ-tile" model with a descriptor-launched, memory-coupled tensor engine. A single MMA_OP instruction (custom-0 opcode, funct3=3, funct7=2) hands the engine pointers and configuration; the engine then autonomously streams operands out of LMEM, runs the full 32×32×K tile computation, accumulates in a private SRAM, writes D back to memory, and signals completion through the transaction-barrier fabric. The issuing warp is free the entire time.

The instruction encodes its descriptor across the two source vector registers, packed per-lane with vx_wgather:

FieldLocationNotes
A, B, C, D pointersrs1[0..3]A/B/C must be LMEM-resident; D is a global address
A/B bitmap pointersrs2[0..1]sparse modes only
tx-barrier idrs2[2]standard (id<<8)|group encoding
flags wordrs2[3][0] flush, [1] init, [3:2] sparsity, [7:4] fmt_s, [11:8] fmt_d, [17:12]/[23:18] compressed block counts, [31:24] K

Motivation (reconstructed from the design and its host recipe): the WGMMA pipeline at NT=32 is limited not by the datapath but by everything around it — 17–32 µops of issue bandwidth per instruction, operand staging through the register file, C-tile writeback through the LSU, and a warp-group's worth of scheduler state. TCU_OP attacks all four at once:

  • Issue amortization: one instruction covers an entire 32×32×K tile op (vs. 256 WGMMA instructions × 17–32 µops for the same 128³ GEMM).
  • Register-file bypass: operands never touch the GPR file; the accumulator lives in a dedicated 32-bank × 32-slot SRAM instead of fragC registers, eliminating the WGMMA C-store epilogue that we measured as a ~45k-cycle K-independent floor.
  • Warp decoupling: the hardware acquire/release contract on the tx-barrier lets one warp orchestrate DXA staging and MMA launches as a software pipeline — the same double-buffer discipline as the WGMMA DXA kernels, but with 1 warp instead of 16.
  • Structured sparsity: bitmap-driven zero-skipping with 32-way sorters compresses A and/or B, shrinking both the memory footprint and the number of issue steps (set_steps = ⌈nzA/2⌉·⌈nzB/16⌉).

Read engine

A single 16-lane (of 32 available) LSU-width port serves all four streams through a rotating arbiter. A/B/bitmap use 2-deep double-buffered windows with request/loaded/active bit-pair tracking; C bypasses buffering and feeds the accumulator directly in overwrite mode (C is the accumulator's initial value, not an addend). A-and-B requests are held back until all C requests have issued (a_req_ready gates on c_blocks_requested == 32), serializing the init phase.

Tile Index Aligner (sparsity front-end)

Per k-step, A's and B's element bitmaps feed two 32-way sorters (VX_tcu_32_way_sorter) that emit, for each compacted position, the original logical index plus a validity mask, and the zero population count. Three things fall out of that single structure: operands are compacted so the FEOP array only ever sees non-zeros; the original indices survive as the accumulator's row/column addresses, so compacted products land at their true output coordinates; and the popcounts set the step counts for this k-step (vertical_steps = ⌈nzA/BLOCK_M⌉, horizontal_steps = ⌈nzB/BLOCK_N⌉), so all-zero steps are simply never issued. That last point is the architecturally load-bearing one and the paper's explicit departure from DSTC, where step-skipping is done in software by issuing only the active steps: moving it into hardware is what lets the engine stay asynchronous — the warp hands over one descriptor and the instruction stream never grows with the sparsity pattern. Three modes are supported: dense (bitmaps forced to all-ones), compressed×compressed (both operands pre-compacted in memory with bitmap metadata), and a hybrid uncompressed-A × compressed-B mode that compacts A online in hardware (a_set_flat_compressed), aimed at the common DNN case of statically-pruned weights against dynamic activations.

Issue FSM and FEOP array

Per k-step (set), the FSM walks step = 0 … vertical_steps·horizontal_steps−1 block positions; at the default 2×16 FEOP geometry a dense set takes 32 cycles (16 vertical × 2 horizontal). Each cycle, one A sub-column (2 elements) is broadcast against a B sub-row (16 elements), producing 32 fmadd products at II=1. The multiply pipes are 3 deep (DPI: FMUL 2 + RND 1); addresses/valids ride a parallel delay pipe.

Accumulator

Products enter a 32→32 VX_stream_xbar keyed by bank(r,c) = (r mod BLOCK_M)·BLOCK_N + (c mod BLOCK_N). In dense execution that mapping is static and every step touches all 32 banks exactly once, so the crossbar is pass-through and the queues idle; it is sparse compaction that produces irregular output addresses, several products targeting one bank in a cycle, and the need for both the crossbar and the per-lane skid queues ahead of it. At the bank, an fp32 adder (DPI call or BHF pipeline) implements read-add-write with a one-stage RAW forward (forwarding_condition) covering the write latency — the paper notes this bank-local placement as a deliberate departure from DSTC, which routes read-modify-write traffic through the crossbar instead.

overwrite selects accum_source = 0 so a C block initializes rather than accumulates. There is no clear-on-flush path, and that is by design: C-init and D-writeback are meant to happen once per output tile while K runs in the inner loop, so the tile stays resident in the accumulator and both costs amortize over K. That intent is what makes §5.3 (the K-chunked continuation path) critical rather than cosmetic.

Completion

At instruction accept, the engine issues a hardware tx-barrier acquire (is_done=0); at flush completion (or the no-flush settle for flush=0 ops), it issues the release. A 1-deep op_ctx FIFO carries the barrier address from accept to release — this depth-1 queue is what limits the engine to one in-flight op.

Genuinely innovative elements worth preserving

  • Instruction-as-descriptor via lane-packed registers. Reuses the vector register file as a descriptor carrier (vx_wgather), avoiding new architectural state or DCR round-trips per op. Clean and cheap.
  • Tx-barrier acquire/release as a completion contract. The engine arms the same barrier the software waits on, at accept-time — so the ordering window is airtight (no wait-before-arm race) and the mechanism composes with DXA's done-events on the same barrier fabric. This is the piece that makes the 1-warp orchestration model work, and it exposed (and now fixed) a real latent bug in VX_wctl_unit for all hardware acquirers.
  • C-as-initializer with accumulator overwrite mode. Folding accumulator initialization into the same xbar/adder pipeline as products (with accum_source=0) avoids a separate clear port on the SRAM and gives fused C-accumulate (D=A·B+C) for free.
  • The Tile Index Aligner. One structure delivers three things at once — operand compaction, restoration of true output coordinates for the accumulator, and popcount-derived step counts that skip all-zero work — for arbitrary per-element bitmaps on both operands. That is a strictly more general sparsity story than fixed 2:4 (which covers one operand at a fixed 50%), and crucially it keeps step-skipping in hardware, so exploiting sparsity never lengthens the instruction stream and never breaks the asynchronous execution model. This is the design's central idea and it is well executed.
  • Hybrid uncompressed × compressed mode. Compacting A online in hardware while B arrives pre-compressed targets the real DNN case — statically pruned weights, dynamically sparse activations — without paying software preprocessing on the activation side.

The gate is correct but costs throughput — see §5.1 and §8.
Diagnosis chain worth noting: defect #7 masked #10 and #11. The original TCU>DXA bank priority (a deliberate design choice, per its comment) kept LMEM response timing perfectly uniform — so responses never aliased and never split, and the design "worked" in the author's quiet-memory single-op tests while deadlocking on any real double-buffered workload. Fixing the deadlock exposed both response-path defects at once. This is the archetypal hazard of validating an engine only against microbenchmarks that leave the rest of the memory system idle: the engine's implicit contract ("my responses arrive whole, in order, one request at a time") was never stated, never asserted, and silently false.

5. Open items

5.1 Debug and non-debug builds disagree open · blocks acceptance

Every run reported as PASSED in this review was built with --debug=2. The same configuration built with --perf=1, and with no flags at all, deadlocks reproducibly at 128³ on the scheduler stall assertion — and still deadlocks with VX_DBG_STALL_TIMEOUT raised to 2,000,000 cycles, so it is a genuine hang, not a threshold artifact. Tracing is a simulation side effect and must not change cycle behaviour, so a define-dependent behavioural difference exists somewhere in the design; the leading hypothesis is reliance on state that is only initialized in debug builds (X-propagation, or VX_dp_ram's RESET_RAM/INIT_VALUE path), in which case the non-debug build is exposing a real reset-coverage hole rather than a new bug. Until this is closed, no functional claim about TCU_OP should be considered established for a normal build, and the cycle count in §8 is provisional. Next step: bisect the small cases (1/2/4 tiles) without --debug to find whether the divergence is size-dependent, then diff the effective define sets between the two builds.

5.2 K-chunked continuation path is unverified — and it is the primary intended mode open · design-critical

The architecture amortizes C-init and D-writeback over K by keeping the output tile resident in the accumulator across k-chunks: init=1 on the first chunk, flush=1 on the last, neither in between. The K field in the descriptor is 8 bits, so K > 255 must be chunked — the continuation path is not an edge case, it is how the design is meant to run. All verified runs here use the opposite shape (SGEMM_TILE_K_MULT=4, one init+flush op per output tile), which works only because K=128 happens to fit in one op and which defeats the amortization the architecture is built around. The continuation path's earlier corruption is now explained by defect #11, but it has not been re-tested since that fix. Re-verifying it (e.g. 128×128×512, four chunks) is the highest-value correctness task after §5.1, and would retire both the workaround and its 64 KB LMEM requirement.

5.3 Performance recovery of the response-path fixes open · perf only

Correctness is settled (1-, 2-, 4-tile and full 128³ all PASSED), but defect #11's single-outstanding-request gate costs ~3.3k cycles/op (§8). Restoring depth-2 prefetch requires per-request reassembly state rather than one per-stream accumulator — i.e. tracking coverage per sequence tag (the bit already encoded in tag.value by fix #10), so two same-stream requests can be merged independently. This is the single highest-value follow-up.

5.4 Kernel metrics readback is dead open · minor

The app prints Kernel body cycles: 0 / instructions: 0 — the vx_rdcycle_sync_* / vx_rdinstret_local path in the kernel epilogue writes zeros (and only from vx_thread_id()==0, which under the CTA_RANK-based warp split may not be the surviving warp). Cycle counts in this review therefore come from trace timestamps (CTA dispatch → cta_done), which is authoritative but inconvenient; the in-kernel counters should be repaired before any tuning campaign.

5.5 Latent defects found by inspection (not yet triggered)

  • Real (non-zero) C initialization is broken. The response path decodes "null C" as c_tile_addr == 0 (op_core:780), but the request FSM clears c_tile_addr when the last C request issues (op_core:389). Every C response arriving after that point — i.e., nearly all of them — is silently zero-filled. Only C≡0 workloads can pass; D=A·B+C with C≠0 will silently compute D=A·B (partially). The null-C flag must be latched at accept, not inferred from a mutating address register. Note this is not a corner case in either direction: continuation chunks legitimately carry no C (a designed mode), while fused D=A·B+C with real C is a first-class GEMM feature the paper assumes — and today only the former can work.
  • Null-C still burns bandwidth. With C=0 the engine still issues all 32 C reads (redirected to A's address, op_core:742) and discards the data — a pure waste of the init phase. It should skip the requests entirely.
  • int8/uint8 format ids collide after truncation. fmt_s is a 4-bit field; modern TCU_I8_ID=17 truncates to 1 (kernel side truncates identically, so it "works" by accident); TCU_U8_ID=18 → 2 collides with fp16. bf16 (3) silently falls to the zero-output default in the FEOP case. The descriptor needs a 5-bit format field or its own compact encoding.
  • K is an 8-bit field (rs2[3][31:24]): K per op ≤ 255, undocumented; K=256 silently wraps to 0.
  • LMEM-only operand contract unenforced. A non-LMEM operand address only prints a debug TRACE (op_core:1454) while the datapath proceeds and then deadlocks on the dcache coalescer's partial-mask responses (32 requests → 128 fragmented returns break the per-block accounting). This should be a RUNTIME_ASSERT.

6. Design flaws & inefficiencies

One framing caveat before the list. Several structures that look extravagant against dense GEMM — the 32→32 crossbar, the per-lane input queues, the sorters, the dynamic step counts — are the sparsity mechanism, and in the dense corner they are provably idle (static conflict-free bank mapping). They are not waste; they are the feature. The items below are things that are genuinely suboptimal on the design's own terms.

SevFlawDetail & cost
critRuntime divide/modulo in the issue pathm = (step / horizontal_steps) << …; n = (step % horizontal_steps) << … (op_core:803–805) — a 32-bit combinational divider feeding per-cycle issue logic. Dense values are powers of two, but the sparse path makes the divisor dynamic — and since dynamic step counts are exactly how hardware step-skipping works, the divisor cannot simply be constrained away. Restructure instead as two nested counters (the horizontal counter's carry increments the vertical one, both reloaded per k-step from the popcounts); the division disappears entirely while keeping the step counts fully dynamic.
crit4× area, 1× useVX_tcu_unit instantiates one full op-core per issue block (assert forces BLOCK_SIZE == ISSUE_WIDTH): at IW=4 that is 4 × (32 fmadd units + 4 KB accumulator SRAM + 32×32 xbar + sorters), of which exactly one is reachable in the single-warp programming model. My bring-up fix routes block 0 and dead-ends the rest, but the right fix is NUM_TCU_OP_CORES=1 (or a real per-block memory arbiter if a multi-warp model is ever intended).
majorHalf-width memory portEvery A/B/C read uses a 16-lane mask on the 32-lane port (mask=0x0000FFFF), and D writes use 16 lanes (wr_mask) — half of each LMEM row access is wasted. Full-row requests would halve the request count and the init/flush phase lengths.
majorZero inter-op pipeliningexecute_ready requires ~busy_r; op_ctx and mdata queues are depth 1. Each op pays serialized prologue (32-cycle C phase gating A/B requests — op_core:123) and epilogue (64+ cycle flush) with the engine otherwise idle. Back-to-back tiles could overlap next-op C-init/A-prefetch with current-op flush for ~100 cycles/tile saved (~1.6k cycles at 128³, plus it removes the double-buffer's dead time).
noteThroughput is area-limited, not shape-limitedAt 2×16 each k-step costs 32 cycles for a 32×32 outer product — 32 MAC/cycle. To be clear, the 2×16 shape itself is a well-argued choice, not an oversight: at a fixed budget of m×n=32 multipliers the design space was swept and 2×16 beats 4×8 on accumulator bank conflicts (fewer distinct row/column residue classes per sparse step), which our own measurements do not contradict. The opportunity is on a different axis — raising the total multiplier count (e.g. 4×16 = 64, 8×16 = 128 MAC/cycle), which grows the A broadcast, adder count and crossbar, but which §8 shows the LMEM port has ample headroom to feed. That sweep was never run.
minorGlobal stall domainfeop_enable = accu_queues_ready freezes the entire datapath (issue, pipes, accu) on any single-lane queue-full; with a TODO admitting the intended condition was never finished (op_core:172).
minorBuffer depths hardcodedA/B/BITMAP_BUF_SLOTS = 2 // "Current code only works for '2'" — the double-buffer bit-pair FSMs (rq/ld/active/load bits) are hand-rolled per stream instead of a generic FIFO abstraction, which is where several of the reviewed state-transition subtleties (and likely the cross-op bug) live.

7. Code-quality audit

  • Dead code: ~250 lines of commented-out trace blocks and abandoned variants (op_core ~140, accu ~100, kernel ~30), including whole commented generate branches (op_core:767–781). Section banners literally named NEW, NEW^2, NEW^3.
  • 15+ open TODOs, several load-bearing: XBAR_LATENCY … "TODO: Not sure if condition is legit"; feop_enable's unfinished condition; "Fix all operations on 32'() to the smallest possible size".
  • Magic numbers: the S2 bitmap block math re-derives (K+15)>>4 inline next to the localparam that encodes the same quantity (op_core:316); matrix ids 1/2/4/8 as bare literals throughout.
  • Null-pointer sentinels woven through the address FSM (c_tile_addr == '0 as both "no C" and "C done") — the source of latent defect §5.3a.
  • Kernel hygiene: redefines __local_mem via #undef to a raw CSR read ignoring the size argument; debug "trace marker" stores (0x12345678) compiled into result buffers by default (SGEMM_TRACE_MARKERS=1); required -Wunused pragma suppressions; both dense and sparse variants interleaved in one 400-line function.
  • Interface discipline: the original code drove a part-select of tag.uuid through an interface (illegal lvalue, broke Verilator codegen) and left the upper tag bits undriven; fixed during bring-up.
  • DPI calls inside always_comb (dpi_fadd/dpi_fmadd) — fine for simulation, but it means the DPI configuration has no synthesizable adder implementation path at all; only BHF is real hardware.
  • Positive: parameterized FEOP geometry, clean latency-modeling pipe-register idiom, consistent banner structure, and honest debug instrumentation (the ACCU_INIT_VALUE poison and flush/gather conflict ERROR traces materially helped this review).

Measured (first verified 128³ run, debug build; kernel span from CTA dispatch to cta_done; numerically PASSED): ~162k cycles — 2.5× the analytic floor. The per-op time is ≈8.8k cycles against a 4.1k ideal (128 k-steps × 32 cycles + ~500 init/flush). The gap decomposes into (a) the conservative single-outstanding-request gate added as part of fix #10: with LMEM response latency of ~90 cycles under DXA-priority bank contention and a 64-cycle per-block consumption window, the A/B streams starve ~26 cycles per block (~3.3k/op) — recoverable by restoring depth-2 prefetch with proper per-request (sequence-tagged) reassembly tracking; and (b) DXA bank-priority theft plus the serialized 32-read C-init phase (~1k/op) — recoverable via full-row accesses and C-phase overlap. With those three recoveries the projected time returns to ≈70–75k cycles. Note also that this run used crossbar queue depth 2 (inherited from custom/run.sh) where the design-space exploration settled on depth 4; that costs nothing in dense traffic, which never queues, but any sparse measurement must use depth 4.

Analytic floor at 2×16: dense compute alone needs 32 cycles/k-step × 128 k × 16 tiles = 65,536 cycles → 64.0 FLOP/cycle — so even fully recovered, the current geometry cannot beat the tuned WGMMA bundle (58k); parity with plain WGMMA+DXA while using 1/16th the warps and no GPR pressure is the realistic best case, and the FEOP-widening path below is where the architecture actually wins.

Why the dense number is the wrong headline. Everything above measures the design's worst case. The architecture's primary throughput axis is sparsity: step counts scale as ⌈nzA/2⌉·⌈nzB/16⌉, so dual-side density reductions compound — halving the density of both operands cuts transferred operand bytes ~2× but cuts issued steps ~4×. Nothing in the dense measurement exercises that, and no sparse configuration was run in this session (the sparse paths remain unvalidated post-rebase, and carry their own unexercised code including the S1 online-compaction logic). A fair assessment of this engine requires a sparsity sweep, and that is the single biggest gap in what we currently know about it.

The secondary axis is area, and the port has room. Per k-step the engine needs one A/B request pair per 32 cycles — roughly 6% utilization of a port it only half-uses in the first place. At 4×16 (64 MAC/cyc) the dense floor halves to 32,768 cycles; at 8×16 (128 MAC/cyc) it reaches 16,384 — territory the WGMMA pipeline cannot follow at NT=32, because WGMMA is bound by staging arithmetic intensity (~11 MAC/staged-byte against the ~45 it would need), not datapath width. Operands resident in LMEM is precisely how TCU_OP sidesteps that wall; DRAM staging bandwidth, shared with DXA, becomes the next binding constraint somewhere around 8×16.
