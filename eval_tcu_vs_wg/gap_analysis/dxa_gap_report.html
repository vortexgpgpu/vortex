Why WGMMA+DXA isn't faster: the DXA critical path

A cycle-level autopsy of sgemm_tcu_wg_dxa vs sgemm_tcu at M=N=K=128, fp16→fp32, NW=16, NT=16, one core. Primary vehicle: simx with per-class MPM counters, cycle-stamped debug traces, and Perfetto exports; rtlsim numbers from the earlier sweep are used for cross-checking.

The answer in three sentences. The WGMMA+DXA design is doing exactly what it promises on the compute side — 44% fewer instructions than the WMMA baseline, and the tensor pipes run at 3.35 of a possible 4 uops/cycle whenever they run. It is slow because the single DXA engine is busy for 92.1% of the entire run and only 6.7% of that time overlaps any compute: the kernel's single-buffer schedule serializes staging against WGMMA, and the engine itself moves data at 3.7 bytes/cycle against a 64-byte/cycle LMEM port. The gap is therefore not expected and not fundamental — it is the compounding of four identifiable implementation bottlenecks (ranked in §4), and once staging is off the critical path the same kernel has roughly a 10× headroom at this problem size.

Re-evaluation, 2026-09-17 — the diagnosis held and the top fixes are in. Two of this report's recommendations were implemented and validated since it was written: register-resident double buffering (recommendation #1, commit bd1420351) and the DXA B-scatter drain fix (the core of recommendation #2, commit fa1765c85, grouped BlockMajor writes). On the improved architecture the headline question inverts: sgemm_tcu_wg_dxa is now 1.49× faster than sgemm_tcu on rtlsim (74,947 vs 111,373 cycles; was 8% slower), rtlsim agrees with the simx model within 3% (74,947 vs 77,176), and DXA LMEM beats dropped 69,632 → 20,480 exactly as §3 predicted — the B drain now takes 128 beats per 1 KB tile instead of 512. 93% of tensor-pipe compute now hides under transfers. The scoped CI matrix (162 WGMMA/DXA cases, both simulators, XLEN 32+64) passes clean. The next wall is exactly the one §4 ranked next: the tbuf operand path (RC4, ~26k stall cycles), now the top open item. 2What the machine is actually doing

The debug trace gives exact busy intervals: every DXA transfer's start/complete pair and every tensor-core uop retirement. Painting them on a common time axis answers "compute vs memory overlap" definitively:

Three numbers from these timelines carry the whole diagnosis:

  • TCU compute is essentially free and essentially perfect. 16,384 uops retire in 4,884 busy cycles at IW=4 — 3.35 uops/cycle against a hard ceiling of 4. When operands are resident, the warp-group machine runs at 84% of peak. (The WMMA baseline manages only 1.14 uops/cycle in its busy cycles — the warp-group lockstep genuinely is the denser way to feed the tensor pipes.)
  • The DXA engine never rests and never shares. Its 256 transfers occupy 71,095 of 77,172 cycles with a total of 808 idle cycles between transfers. It is the critical path; everything else is waiting for it.
  • Overlap is 6.7%. The single-buffer schedule (stage → barrier → compute → barrier → re-stage) makes staging and compute mutually exclusive within a CTA; the only overlap comes from other resident CTAs' transfers draining while one CTA computes.

3Where the DXA cycles go

The engine's 71k busy cycles moved 256 KB of tile data (128 A-transfers + 128 B-transfers of 1 KB each). Pairing each transfer's start/complete with its descriptor slot splits the cost:

transfercountGMEM lines readLMEM write beatsbytes / beatspan avgspan mediancycles / KB
A tile (32×16 fp16, row-major dest)128323232 B371266371
B tile (16×32 fp16, BlockMajor dest)128161288 B184150184

Both rows are pathological, for different reasons:

  • A pays DRAM latency, twice over. A's tile rows are 32-byte segments of rows with a 256-byte stride, so every one of its 32 line reads returns 50% useful bytes — 2× the necessary DRAM traffic. Worse, the engine caps in-flight reads at 8 (VX_CFG_DXA_MAX_INFLIGHT), so a 32-line transfer exposes ~4 serial DRAM latencies. A single 1 KB A tile takes a median 266 cycles — ~10× the port-limited minimum.
  • B pays scatter write amplification. The BlockMajor destination layout interleaves K inside each 64-byte block, so one GMEM line (one k-row of the tile) scatters 4 fp16 elements into each of 8 different LMEM blocks — 8 beats of 8 bytes each. Each LMEM block is written 8 times by 8 different beats. The port could carry the whole tile in 16 beats; the scatter takes 128.
  • Transfers never pipeline into each other. The lone worker (VX_CFG_NUM_DXA_CORES = max(1, cores/8) = 1 on this config) runs address-generation → read → drain per transfer and only then starts the next, so all 256 transfers pay their startup latency serially. Average span × count ≈ the whole DXA phase: 277.7 × 256 = 71k cycles.

4Root causes, ranked

RC1Staging is serialized against compute — by schedule, not by necessity≈ 66k of 77k cycles

The kernel's single-buffer loop (stage tile i → barrier → compute i → barrier → overwrite) makes every warp in the CTA sleep through every transfer: scheduler idle is 82%. Overlap exists only across co-resident CTAs and covers 6.7% of DXA time. This schedule was adopted because the double-buffered variant measured worse — §5 shows that failure is a compiler artifact, not evidence that overlap doesn't pay.

RC2The DXA engine drains at 5.6% of LMEM port bandwidth71k cycles for 256 KB

Three multiplicative engine losses: B's BlockMajor scatter lands 8 bytes per beat where the banked LMEM port accepts 64 (the RTL's own warp-array transpose writes full blocks — the engine could gather across k-rows the same way); A's half-used line reads double its DRAM traffic; and the 8-deep in-flight window plus no cross-transfer pipelining expose one full memory latency per 1 KB transfer. Fixing the scatter alone takes B from 128 to 16 beats; letting the next transfer's AGU run during the current drain removes ~256 serial latency exposures.

RC3CTA size is welded to ISSUE_WIDTH → tiny CTAs → zero data reuse4× (IW=4) to 16× (IW=1) traffic

The host derives warps-per-CTA from VX_CAPS_ISSUE_WIDTH because the WGMMA lockstep gate dispatches exactly ISSUE_WIDTH warps. At IW=4 that means 16 CTAs for a 128² output; each re-DMAs the same B tiles from DRAM (gmem_dedup=0, no multicast used, DXA bypasses every cache). The engine reads 384 KB of DRAM to deliver 64 KB of unique matrix data, while the WMMA baseline's dcache turns the same reuse into 70–93% hit rates for free. At IW=1 this same coupling produces single-warp CTAs, 1,024 transfers, 16× B re-staging — plus TCU-side serialization from the CTA-overlap fence on the shared B-buffer. This is the main reason the IW=1 column is catastrophic.

RC4TCU operand refetch through a 1-line/cycle tbuf porttbuf stalls ≈ 10% of cycles

Every WGMMA instruction group re-plans its operand tile into the tile buffer through a single LMEM port at one 64 B line per cycle — 32 lines (16 A + 16 B) before any uop advances, and the lockstep gate holds all four blocks until the slowest is resident (tbuf_stalls = 7,570 ≈ 9.8% of cycles; tbuf_cache_hits = 19 of 128, because the shared B-buffer is invalidated whenever the WGMMA pipeline drains — which the barrier forces every tile). Data staged into LMEM once is thus re-read 1.7× (6,978 lines for a 4,096-line minimum). Secondary today because RC1/RC2 hide it; it becomes the next wall once staging overlaps.

5The double-buffer trap: why the "obvious fix" measured 8× worse

Overlap should erase RC1, and DXA_DOUBLE_BUFFER exists in the kernel — but it measured 3.4–4.5× worse on rtlsim and 8.3× worse on simx (637,819 cycles). The trace pins the mechanism precisely:

  • With two buffers the buffer index p becomes runtime-varying, so the compiler can no longer scalarize A_buf[2], B_buf[2], and the two vortex::barrier objects into registers — they land on the per-thread stack (11 spill stores appear; frame grows 0x30→0x50).
  • The hot reload sites bracket every vx_bar: the barrier object and buffer pointers are re-loaded from the stack in every loop phase. Dynamic loads triple: 35,840 → 100,352.
  • Per-lane stacks live in global memory 8 KB apart, so one spill reload fans out to 16 uncoalesced DRAM lines (coalescer misses: 256 → 18,944; DRAM reads: 8,210 → 77,570) at 231-cycle average load latency, and the added DRAM pressure drags DXA line latency from 278 to 725 cycles.

Verdict: the failed experiment convicts the compiler/ABI path (per-lane stack in DRAM), not the pipelining idea. A manually 2×-unrolled loop with two statically-named buffer/barrier sets — no runtime-indexed arrays — keeps everything in registers and should recover the overlap that RC1 costs.

Is the gap "expected"?

DESIGNPartly, at this problem size. 128³ streams comfortably through a 16-warp dcache-backed WMMA kernel (70% hit rate, latency hidden by warp parallelism), so the baseline is strong and DXA's fixed costs dominate its benefits. The K=512 result (1.73× win) shows the crossover exists. FLAWMostly not. A staging engine at 5.6% of port bandwidth, zero cross-transfer pipelining, one worker for the whole cluster, and 4–16× redundant DRAM traffic with the multicast/dedup hardware sitting unused are implementation gaps, not design intent. "On paper" — overlapped staging at even half the LMEM port rate — this kernel is compute-plus-tbuf-bound at roughly 8–12k cycles, i.e. ~10× faster than the WMMA baseline instead of 1.28×. TOOLCHAINThe double-buffer failure is a spill/ABI artifact (runtime-indexed locals + per-lane stacks in DRAM). It blocked the single most valuable optimization and sent the earlier investigation down a "double buffering doesn't pay" path.

7Recommendations, in payoff order

  1. [DONE, bd1420351] Re-enable overlap without the stack. Landed — not as the unroll sketched here, which was tried and lost 2.5× to callee-save stack bursts, but as an XOR-toggle of buffer pointers and barrier ids that keeps all pipeline state in caller-saved registers (see the double-buffering proposal). Verified by the trace method as specified: 93% of compute now overlaps transfers. As predicted, its cycle gain waits on the tbuf wall (#5) now that staging is cheap.
  2. [DONE, fa1765c85] Fix the B scatter drain (DXA engine). Landed as a grouped drain in the RTL write stage: the same-word elements are contiguous in the source line, so one masked write per beat replaces tcN element beats — 512 → 128 beats per tile, matching the model exactly (the further 128 → 16 by gathering across k-rows remains open). Measured: rtlsim 116,949 → 74,947, wg_dxa now 1.49× faster than the WMMA baseline on RTL (rtlsim drain proposal).
  3. [OPEN] Pipeline transfers in the worker + widen A reads. Start transfer i+1's AGU/reads while i drains; raise DXA_MAX_INFLIGHT 8→32; teach the A descriptor path to fetch two tile-rows per 64 B line (or store A K-major). Removes ~256 serial latency exposures and halves A's DRAM traffic.
  4. [OPEN] Exploit reuse: multicast or bigger CTAs. The mcast path (sgemm_tcu_wg_dxa_mcast, gmem_dedup) exists precisely for RC3 — B tiles should be fetched once per core, not once per CTA. Longer term, decoupling CTA width from ISSUE_WIDTH in the lockstep gate removes the root coupling.
  5. [NOW THE ACTIVE WALL] Revisit the tbuf. With #1/#2 landed this is the top open item: RC4's single-outstanding demand fetch costs ~26k stall cycles of the 74,947, and fast-engine probes bound the payoff at roughly the next 15–20%. A tested caveat from the follow-up work: re-prioritizing the shared DMA arbiter alone cuts tbuf stalls 2.4× but buys zero cycles until the fetch is pipelined — land them together.
  6. [CLOSED at IW=4 / superseded] The rtlsim/simx gap. The follow-up rtlsim investigation localized the divergence to the element-wise drain (the no-DXA kernel already matched to 1.4%); with #2 landed, RTL and model agree within 3% at IW=4. IW=1 re-measured on the improved architecture: 149,591 cycles vs the model’s 142,480 — a 5% gap, closed as well (was 2.4×). What remains at IW=1 is a real architecture story, not a simulator artifact: wg_dxa still trails the WMMA baseline there (129,514) because single-warp CTAs forfeit reuse and serialize on the CTA fence — RC3, addressed by recommendation #4.
