Bug-fix and optimization dossier for review

A self-contained account of (1) defects verified to exist in upstream vortex/master and fixed on this branch, and (2) performance optimizations identified, implemented, and validated — each with the analysis finding that motivated it, the mechanism of the fix in prose (no source code), why it works, measured results, and an explicit confidence assessment. Intended reader: a reviewing agent with access to the repository. Companion evidence documents: the DXA critical-path report, the double-buffering proposal, and the rtlsim drain proposal.

Context for the reviewer. The subject system is the fork's outer-product sparse tensor-core extension (TCU_OP): a WGMMA warp-group matrix pipeline fed from local memory (LMEM), plus a DXA asynchronous data-movement engine (a TMA analogue) that stages tiles from global memory into LMEM with layout transformation, synchronized through transaction barriers. Reference workload throughout: sgemm_tcu_wg_dxa at M=N=K=128, fp16→fp32, 16 warps × 16 threads, ISSUE_WIDTH=4, one core, compared against the per-warp-WMMA baseline sgemm_tcu. Two simulators: simx (cycle-level architectural model) and rtlsim (Verilated RTL). Methodology: MPM performance-counter classes, cycle-stamped instruction/engine traces with interval analysis, Perfetto exports, kernel disassembly audits, and controlled A/B experiments — including two candidate fixes that were tested and rejected, noted where relevant. All commits are local to the branch; nothing is pushed.

Part 1 — Defects verified in upstream vortex/master, fixed here

Each of the four patterns below was checked verbatim against upstream master before being classified as an upstream defect (not a fork artifact). Confidence scores are for "the fix is a true, clean correction suitable for upstreaming," on a 0–5 scale, carried over from the dedicated verification pass and unchanged by subsequent regression coverage (all four fixes survived a 294-passing-case CI sweep untouched, plus this session's WGMMA/DXA-focused matrix).

BUG-1DXA BlockMajor destination layout ignores the FEDP2K geometry changesilent data corruption · active in master

Finding that exposed it

Every WGMMA configuration built with the FEDP2K option (which doubles the dot-product unit's K-depth per step) produced wrong results whenever tiles were staged by the DXA; the same kernels passed with cooperative software loads. Diffing the staged LMEM image against the golden layout function in the kernel-side tensor header showed the DXA scattering elements to the positions the non-2K geometry would use.

Defect

The BlockMajor destination-address computation in the DXA's LMEM write stage (RTL scatter unit, mirrored in the simx DXA model) derives block indices and intra-block offsets from the tile geometry — but the K-span of a block is a function of the FEDP depth, and the FEDP2K build doubles it. Five terms of the destination arithmetic (the per-beat step, the block-wrap step, the block-index shift, the K-word masking, and the block-row decomposition) were computed as if the K-span were the base value. The engine therefore wrote a layout the tensor core's B-buffer never reads correctly. Nothing faults: it is silent corruption.

Fix and why it works

A single compile-time log-ratio constant (0 for base, 1 for FEDP2K) is folded into each of the five terms, in both the RTL and the model. This restores the invariant the whole path depends on: the producer's destination formula must be congruent with the consumer's read formula (the same algebra appears in the kernel header's index function and in the B-buffer's fetch wiring), and that algebra is parameterized by the FEDP depth everywhere else already. The fix is a completion of the parameterization, not a workaround.

Validation & confidence

FEDP2K×DXA configurations went from failing to passing on both simulators; non-2K configurations byte-identical. CONFIDENCE 4/5 — clean fix; the missing point is upstream test coverage (recommendation: add a FEDP2K case to the DXA test catalog so the invariant is pinned).

BUG-2Tensor B-buffer cannot hold dense blocks spanning two bank rows; unguarded sub-block offset wrapswrong operands on affected geometries

Finding that exposed it

Dense WGMMA at the 16-thread geometry read garbage B operands for the second half of each block: the B-buffer's resident-slot bookkeeping assumed one bank row per dense block, but at this geometry a dense block occupies two. Separately, an offset term used to select the sub-block within a warp-group tile was computed by masking even when the configuration defines only one sub-block — the mask then wrapped the offset into a neighboring block's storage.

Defect

Two related gaps in the B-buffer (RTL tensor-core operand buffer): (a) the fetch/residency state machine tracked a single dense bank-row slot, so geometries whose block straddles two rows fetched only the first and served stale or unrelated data for the second; (b) the sub-block offset was always masked-arithmetic, valid only when the sub-block count exceeds one.

Fix and why it works

(a) The dense path gained a second resident slot and a two-fetch sequence so a block's full extent is resident before any consuming step advances — the same discipline the sparse path already used for its two-row blocks, extended to dense. (b) The sub-block offset is forced to zero when the configuration declares one sub-block, making the mask arithmetic unreachable exactly where its precondition fails. Both changes align the buffer's state machine with the geometry algebra it serves.

Validation & confidence

Affected dense geometries pass on both simulators; unaffected geometries unchanged. CONFIDENCE 3/5 for the two-slot extension (the XLEN=64 and K-major spill corners of the buffer are not exercised by existing tests — this session's 64-bit WGMMA/DXA CI sweep, running at time of writing, addresses part of that gap); 5/5 for the offset guard alone, which is a strict precondition fix.

BUG-3simx functional-unit lock released at issue of the last uop, not at acceptance — deadlockmodel-only hang · reproducible in master

Finding that exposed it

A reproducible livelock: WGMMA sgemm at 4 threads, K=1024, issue width < 8 hangs forever in the model (never in RTL). Drain-history instrumentation showed two warps each holding half of a functional unit's resources, each waiting for the other's half.

Defect

The model's sequencer expands multi-step instructions into micro-op chains carrying "lock the functional unit" on the first uop and "unlock" on the last. The unlock was applied when the last uop issued. Between issue and the functional unit's acceptance of that uop sit the operand collectors and a response arbiter, which can legally reorder warps. A second warp's chain could therefore acquire the lock and interleave into the unit while the first chain's tail was still in flight — each chain then blocks the other's completion. This is a model-fidelity bug: the RTL's issue path does not have the equivalent window.

Fix and why it works

The unlock is deferred: at issue of a chain's last uop the model records a pending release keyed by issue-slot and unit; the release executes at the point the functional unit accepts that uop (the same place credits return). This makes lock release atomic with resource handoff — the invariant the lock exists to provide — rather than atomic with issue, which was never sufficient. A controlled A/B (fix reverted, caches cleared, same seeds) shows bit-identical instruction and cycle counts on non-hanging workloads: the fix changes no timing, it only removes the illegal interleaving.

Validation & confidence

The K=1024 hang is gone; parity numbers unchanged. CONFIDENCE 4/5 — the deferred-release structure is the principled fix; the held-back point is that a full model-parity sweep across the catalog should accompany upstreaming since the change touches the central issue loop.

BUG-4DXA completion counting fires on request-valid without request-readylatent barrier-accounting corruption

Finding that exposed it

An (ultimately reverted) experiment in LMEM bank arbitration created backpressure on the DXA's write path and immediately corrupted transaction-barrier accounting: barriers released early or never, though the experiment itself touched no barrier logic.

Defect

The per-bank write-fire signals that feed the DXA completion detector (which converts the final write of a transfer into a barrier event) were derived from request-valid and the byte-enable mask alone. Under backpressure a stalled beat stays valid for multiple cycles and is counted repeatedly. Upstream's default arbitration happens never to stall that path, so the bug is latent in master — but any change to arbitration, banking, or timing arms it.

Fix and why it works

The fire condition is additionally qualified with request-ready, making "fire" mean the transaction was accepted this cycle — the universal handshake convention the rest of the design uses. One condition, no behavioral change in the unstalled case.

Validation & confidence

With the fix, the arbitration experiment no longer corrupts barrier state; default behavior identical. CONFIDENCE 5/5 — handshake hygiene with a demonstrated failure mode.

Part 2 — Performance optimizations: analysis, mechanism, results

OPT-1Grouped BlockMajor scatter drain in the DXA write stage (RTL)rtlsim 116,949 → 74,947 cycles (−36%)

Analysis that inspired it

The end-to-end investigation established a chain of three facts. First, interval analysis of engine traces showed the single DXA engine busy for 92% of the reference kernel's runtime with only 7% of that time overlapped by compute — the engine is the critical path. Second, the model/RTL divergence was localized to the DXA: the WGMMA-without-DXA variant matches between simulators to 1.4%, while the DXA variant diverges 1.5×. Third, a cycle trace of the RTL engine showed each 1 KB BlockMajor B tile draining in 512 single-element beats — two useful bytes per beat through a 64-byte LMEM port — where the model (and the port) support gathered beats. One run moves 69,632 write beats where 20,480 suffice. A tempting alternative explanation (a 43× global-memory read amplification suggested by the DXA performance counters) was chased and disproven: the counters are broken (traced fire counts differ from counter values on a deterministic run), which is recorded separately as measurement debt.

Optimization and why it works

The BlockMajor layout has an algebraic gift: the tcN consecutive elements that belong to one destination LMEM word are contiguous in the source cache line (they are consecutive along the tile's N axis), and their destination offsets within that word form a fixed power-of-two stride. Gathering them therefore requires no crossbar and no data-dependent routing — a bounded spread network takes a contiguous byte run from the fill buffer and places its elements at the constant stride, emitting one masked write per cycle instead of tcN writes. The read cursor advances by a group per beat and the destination address by exactly one block per beat, which simplifies the address bookkeeping (the previous per-element step/wrap alternation collapses to a single constant). Alignment is structural — tile rows and cache-line boundaries are both multiples of the group — so groups never straddle destination words; a shorter tail group is handled by the existing fill-level masking; and configurations whose group span exceeds the LMEM word (e.g. FEDP2K today, some 64-bit geometries) are detected by a static fits-check and take the untouched element-wise path, so correctness never depends on the new mode. A deliberate side effect: the grouped profile is exactly what the simx model already assumed, so the change closes a model/RTL divergence rather than opening one.

Results and validation

Reference kernel on rtlsim: 116,949 → 74,947 cycles; the WGMMA+DXA kernel goes from 7% slower than the per-warp-WMMA baseline (111,373) to 1.49× faster; RTL now within 3% of the model (77,176). Beat counters land exactly on the predicted 20,480. Validated additionally on: a one-CTA smoke size (beats exactly at target, −18% cycles), the multicast application (replay operates per emitted word, unchanged semantics), the FEDP2K build (fallback path exercised, passes), and the double-buffered kernel. A companion negative result matters for review: re-prioritizing the shared LMEM-DMA arbiter in favor of tensor-core reads — a plausible fix — was implemented and measured first, cut operand-fetch stalls 2.4×, and changed total cycles by noise, because those stalls were hidden under the drain critical path. It was reverted and re-ranked to accompany the next-wall work rather than shipped as a fix that "should" help.

OPT-2Register-resident double buffering for the DXA-fed WGMMA kernelrecovers an 8.3× regression into a small win; enables overlap

Analysis that inspired it

The critical-path report showed the kernel's single-buffer schedule serializes staging against compute (80–90% scheduler idle; overlap only from co-resident thread blocks). The existing opt-in double-buffer implementation measured 8.3× worse on the model and 3–4.5× worse on RTL. Tracing its dynamic loads found the mechanism, which generalizes beyond this kernel: this architecture's per-lane stacks live in global memory at an 8 KB stride, so one stack-resident word costs sixteen uncoalesced accesses that all map to the same cache bank — one spilled value ≈ sixteen serialized DRAM round-trips. The original ping-pong selected buffers and barrier objects through runtime-indexed local arrays, which the compiler cannot promote to registers; the synchronization objects were re-loaded from the stack around every barrier in the hot loop. A first rewrite (unrolling the loop two-fold over statically named buffers) eliminated hot-loop spills yet still ran 2.5× slower: its larger live set added roughly five callee-saved registers, and the prologue/epilogue save bursts — paid per warp, re-paid per thread-block wave — stalled the data cache for ~100k cycles. The derived design rule: a pipelined schedule is viable on this machine only if its entire loop-carried state fits in caller-saved registers.

Optimization and why it works

Keep the single-buffer loop shape — same body, same two-phase barrier protocol per buffer (staging complete; readers done) — and switch buffers by mutating state in place rather than selecting it: the two buffer pointers and the packed barrier identifier are exclusive-or-toggled between two precomputed constants each iteration, and raw barrier intrinsics take the identifier by value so no synchronization object exists in memory at all. Net register cost over the serial schedule is two loop-invariant constants; the compiled body is one instruction longer than the serial version, the stack frame is smaller, and the loop contains zero stack accesses — the prior failure mechanism is structurally impossible rather than merely avoided. The schedule prefetches tile i+1 into the idle buffer before waiting on tile i, and the release/prefetch conditions pair off so an odd tile count needs no tail code.

Results and validation

Model: 637,819 → 76,300 cycles (slightly ahead of the serial schedule's 77,176); RTL: 119,580 with the stock drain, 75,052 on the fixed drain. Passes at issue widths 1 and 4, odd tile counts, and K up to 512. An honest bound is part of the result: with the drain fixed, staging is no longer the critical path, so overlap currently buys ≈0 — the trace shows 93% of tensor-core compute already hidden under transfers. The optimization's present value is that the pipeline is now safe and free (previously it was a trap), and it becomes load-bearing when the next wall (operand-fetch pipelining, below) is removed. Emulating a faster engine with configuration knobs (more workers, deeper in-flight) showed the pipeline winning 4.4% at the crossover point, confirming the mechanism.

OPT-3Serial-schedule refinement: drop the final buffer-release barrierminor; −2.3% at reference config

From the same barrier-protocol analysis: the serial schedule's last iteration released the tile buffer for a re-staging that never comes. Removing the dead release phase (the release is conditional on a subsequent tile existing) saved one full-CTA barrier round-trip per kernel, measured at about 2.8k cycles at the reference configuration. Included for completeness; mechanically trivial.
