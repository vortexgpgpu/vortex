Register-resident double buffering for WGMMA+DXA

Why the first double-buffering attempt lost 3–8×, the design rule that failure teaches, a pipeline that obeys it, and the measurements showing it holds up. Companion to the DXA critical-path report.

IMPLEMENTED & VALIDATED · commit bd1420351 · simx + rtlsim PASS

Summary. Double buffering never failed because overlap doesn't pay — it failed because both prior formulations forced pipeline state onto the SIMT stack, and on Vortex one spilled word costs sixteen uncoalesced, same-bank DRAM round-trips (per-lane stacks sit in global memory at an 8 KB stride). The fix is a schedule whose loop-carried state is three registers mutated in place — buffer pointers and the barrier id are XOR-toggled, with raw barrier intrinsics instead of barrier objects — so the hot loop touches the stack exactly zero times. Measured: the old 8.3× regression becomes a 1–4% win on both simulators, correctness holds across IW, odd tile counts and K sweeps, and 93% of tensor-core compute now hides under DXA transfers. Today's gain is deliberately small — the DXA engine is still 87% of the critical path — and §5 quantifies exactly when this structure starts paying its real dividend.

1Post-mortem: two ways double buffering died

Both failures share one amplifier. Vortex gives each thread a private stack in global memory, lanes 8 KB apart. A single spilled word therefore becomes a 16-lane access whose addresses all map to the same dcache bank (8 KB is a multiple of the bank stride): sixteen serialized, write-allocating DRAM round-trips at ~230 cycles each — per execution of that one instruction. Any double-buffering scheme that grows the kernel's memory-resident state gets destroyed by this amplifier before overlap can help.

v1Runtime-indexed arrays — spills in the hot loop637,819 cyc · 8.3× worse

The original ping-pong kept A_buf[2], B_buf[2], bars[2] and selected with a runtime-varying p. SROA cannot scalarize a runtime-indexed aggregate, so the two vortex::barrier objects lived on the stack and were re-loaded around every vx_bar in the k-loop. Dynamic loads tripled (35,840 → 100,352), coalescer misses went 256 → 18,944, and the spill traffic's DRAM pressure dragged DXA line latency from 278 to 725 cycles.

v22×-unrolled with named buffers — spills moved to the prologue, still fatal188,262 cyc · 2.5× worse

Unrolling the loop over two statically-named buffer/barrier sets produced a spill-free loop body — and still ran 2.5× slower. The unrolled body's larger live set (two pointer pairs, two barrier objects, duplicated temporaries across the WGMMA asm blocks) pushed ~5 values into callee-saved registers, whose save/restore bursts hit the same 16-lane stack amplifier once per warp. With 16 CTAs launching in four waves, each wave re-paid the burst: the dcache logged 103,071 bank-stall cycles, the timeline shows 12–19k-cycle dead zones at every wave boundary, and the DRAM contention stretched DXA spans from 278 to 422 cycles average. (This attempt also exposed a schedule bug worth recording: a loop-end restage of the second buffer duplicated the next iteration's loop-top prefetch — 352 transfers instead of 256. The counter dxa.transfers catches this class of bug instantly.)

Design rule. On this architecture a double-buffering schedule is only viable if its entire loop-carried state fits in caller-saved registers: no runtime-indexed locals, no memory-resident synchronization objects, no live-set growth that triggers callee saves. Select buffers by mutating state, never by indexing it.

2Design: toggle, don't select

The proposal keeps the single-buffer loop shape — same body, same barrier protocol, no unrolling — and swaps buffers by XOR-toggling three registers in place:

  • Pointers: A_cur ^= a_tog, B_cur ^= b_tog, where the toggles are loop-invariant constants (ptr0 ^ ptr1) computed once from the LMEM carve-out.
  • Barrier: the vortex::barrier objects are gone. The packed barrier id (slot in bit 8, CTA slot in the low byte — the same encoding the class used) lives in one register and toggles with bar_cur ^= 0x100; the kernel calls vx_barrier / vx_barrier_expect_tx / vx_dxa_issue_2d_wg directly with it.

Net register cost over single-buffering: two loop-invariant constants. The generated body is 147 static instructions vs the single buffer's 146, the frame shrank from 0x30 to 0x20 bytes, and the kernel contains one stack access total (the ABI ra save). The v1/v2 failure mechanism is not avoided by care — it is structurally impossible.

Schedule and phase protocol

load_tile(A_cur, B_cur, bar_cur, 0);                 // prologue: stage tile 0
for (i = 0; i < num_k_tiles; ++i) {
  if (i+1 < n)                                       // prefetch tile i+1 into the
    load_tile(A_cur^tog, B_cur^tog, bar_cur^0x100,   //   other buffer; its readers
              (i+1)*tileK);                          //   were released at i-1
  vx_barrier(bar_cur, nw);                           // wait: tile i staged (tx events + warps)
  compute_tile(A_cur, B_cur);                        // WGMMA accumulate
  if (i+2 < n)
    vx_barrier(bar_cur, nw);                         // release: buffer may restage at i+1
  A_cur ^= a_tog;  B_cur ^= b_tog;  bar_cur ^= 0x100;
}

    compute 2 + release   :c2, 9, 10

Each barrier id alternates two phase types — staged (waits on the DXA's expect_tx completion events plus all warps) and released (warps only). The release of buffer X at iteration i is exactly what licenses the prefetch into X at iteration i+1, so the conditions pair off (i+1<n prefetch ↔ i+2<n release) and the loop needs no tail: an odd tile count simply ends on the other buffer. The expect_tx-before-issue ordering is race-free because vx_barrier suspends the issuing warp until the whole CTA has passed the preceding release phase.

4Why the gain is small today — and when it gets big

Per tile, single-buffering costs t_stage + t_compute; the pipeline costs max(t_stage, t_compute). Overlap's payoff is therefore min(t_stage, t_compute) — and right now that min is tiny: the DXA engine holds 87.5% of the v3 critical path while all WGMMA compute fits in 6.6%. Double buffering today buys the ~5k cycles compute used to add, nothing more. This is the expected result, not a disappointment — the companion report's RC2/RC3 fixes (scatter gather-to-full-blocks, cross-transfer pipelining, multicast) are what shrink t_stage, and each of them raises the value of this structure:

The end-state arithmetic: with RC2-level staging (≈16 beats per B tile, pipelined transfers) a k-tile stages in ~50–80 cycles while compute+tbuf costs ~100–150 — at that point the pipeline hides staging entirely and the kernel becomes tensor-pipe-bound, which is the design's original promise (≈10× over today, per the report's roofline). Without this structure in place first, none of the engine work can show up in end-to-end numbers.

5Limits, risks, and rollout

  • IW=1 stays off. With single-warp CTAs, 16 resident CTAs × up to 4 outstanding transfers oversubscribe the 16-deep DXA queue; prefetch adds churn with no compute to hide (measured +4%). Keep DXA_DOUBLE_BUFFER opt-in, or gate it on ISSUE_WIDTH ≥ 2 if it becomes a default. Raising VX_CFG_DXA_QUEUE_SIZE to 4 × resident CTAs removes the constraint.
  • LMEM footprint doubles (host already sizes it: 2×(cta_M+xtileN)×tileK×2B — 4 KB at IW=4/NT=16, comfortably within LMEM).
  • Compiler fragility. The scheme relies on the toggles staying register-allocated; the guard is the committed evidence (147-instr body, single (sp) op). A CI-friendly tripwire: fail the tensor suite build if kernel_main's frame exceeds 0x30 or its body contains an (sp) access between the first and last vx_bar — both greppable from kernel.dump. Note the dump prints hex offsets: grep \(sp\), not [0-9]+\(sp\).
  • Toolchain follow-up (upstream-worthy): the root amplifier — per-lane stacks in DRAM at 8 KB same-bank stride — punishes every kernel, not just this one. Options worth a separate investigation: placing thread stacks in LMEM when a kernel's footprint allows, swizzling the per-lane stack stride to spread banks, or teaching the backend to SROA small constant-size local arrays under divergence-free indexing.
  • Rollout: landed as commit bd1420351 on tcu-op (local, not pushed; push is your call). The old v1 behavior is gone; the define keeps its name, so existing -DDXA_DOUBLE_BUFFER configs pick up the fixed pipeline automatically. Suggested follow-on testcase for the CI catalog: a dxa.yaml case running sgemm_tcu_wg_dxa with -DDXA_DOUBLE_BUFFER at K=144 (odd tiles) on both drivers.
