Fixing the rtlsim bottleneck: the grouped scatter drain

Why the RTL runs sgemm_tcu_wg_dxa 1.56× slower than the simx model and 7% behind the WMMA baseline, the investigation that found and disproved candidate causes, and the fix — prototyped, measured, and validated. Third installment after the DXA critical-path report and the register-resident double-buffering proposal.

P1 PROTOTYPED & MEASURED · 116,949 → 74,947 cycles · all validation PASSED

Summary. The RTL's DXA engine drains BlockMajor B tiles one element per LMEM beat — 512 beats and 512 cycles per 1 KB tile where 16 would saturate the 64-byte port. That single microarchitectural shortcut is the rtlsim bottleneck: it quadruples the engine's port time versus the simx model (69,632 vs 20,480 beats per run) and puts the drain on the critical path for most of the kernel. The fix is a grouped drain: the tcN elements bound for one destination word are contiguous in the source line, so a bounded spread network emits them as one masked write per cycle. Prototyped in VX_dxa_smem_wr.sv (~60 lines, with a guarded fallback), it takes the kernel from 116,949 to 74,947 cycles at IW=4/128³ — wg_dxa goes from 7% behind the WMMA baseline to 1.49× ahead, and rtlsim now lands within 3% of the architectural model. Two further fixes (bbuf prefetch, TCU-first DMA arbitration) address the next wall, and two candidate causes were tested and rejected along the way — including one that looked damning but was a broken perf counter.

2Findings

F1Element-wise BlockMajor drain — the bottleneck512 vs 16 beats/tile · confirmed by trace

A DBG_TRACE_DXA cycle trace of a minimal run shows each 1 KB B tile draining in 512 single-element beats (smem-wr-fire count=511): the scatter path advances one element per cycle (km_rd_off_r += elem_bytes), each beat carrying 2 useful bytes through a 64-byte port. Per run that is 69,632 beats (A rows drain 32B/beat and are fine; B is 92% of the beats). The simx model gathers same-word elements into 8 beats per line — this one difference is almost exactly the 4× engine-throughput gap, and since the earlier report showed the DXA engine owns >90% of the critical path, it is almost exactly the end-to-end gap.

F2WGMMA operand fetches serialize behind the drain — but are hidden todaytbuf_stalls 37,375 vs 7,570 (model)

RTL routes TCU tile-buffer reads and DXA writes into one lmem_dma port through a priority arbiter with DXA at index 0 (the model gives each its own port), and the bbuf demand-fetches bank-rows with a single outstanding request — ~5k fetches × ~8-cycle serial round-trips ≈ the 37k stall count. Both effects are real and measured — and both are currently hidden under F1 (see the rejected experiment below).

REJECTED"Fix the arbiter priority" — tested, no effect today118,107 vs 116,949 (noise)

Swapping the DMA arbiter to TCU-first (honoring the bank-level "TCU > DXA > LSU" intent already in VX_local_mem) cut tbuf_stalls 2.4× (37,375 → 15,447) yet moved total cycles by −1% noise: the relieved stalls were not on the critical path — warps just waited at the barrier instead. The edit was reverted. It becomes worth landing with P1/P2, when TCU fetch latency is exposed; alone it is a no-op, and this experiment is why it is ranked third, not first.

REJECTED"43× GMEM read amplification" — a broken perf counter, not real trafficcounter 160 vs 96 traced

The DXA perf counters report absurd read counts (166,672 line reads at 128³ where the trace fires 6,144-class numbers, and 160 vs 96 actual on a minimal run — while the DRAM controller sees ~8k) and an avg_gmem_lat in the thousands. The request path itself is clean — one fire per line, slots released on drain_complete, no refetches. The perf_gmem_reqs/gmem_span accumulation in VX_dxa_gmem_req.sv/VX_dxa_worker.sv is what's wrong. Two hours of this investigation went to disproving the phantom amplification these counters implied — fixing them is P4, purely so the next investigation doesn't pay that tax.

F3Long response-bus holds during element-wise drainssecondary

The gmem response for a line is held on the socket's shared response bus while the line drains (rsp_ready gated on the write side); at 512 beats/tile those holds are long and the socket response channel is shared with the dcache. The grouped drain shortens holds 4× as a side effect; explicit response buffering is kept as an optional P5.

3P1 — the grouped scatter drain (implemented)

The observation that makes the fix cheap: in the BlockMajor layout, the tcN consecutive elements of one n-block are contiguous in the source line (consecutive n) and land in the same destination word at a fixed power-of-two stride. So a drain beat can take tcN × elem_bytes contiguous source bytes and spread them through a bounded shift network into one masked 64-byte write:

// per beat, BlockMajor grouped mode:
//   source:  fb_data[km_rd_off +: tcN*elem_bytes]      (contiguous)
//   dest:    lane j at  km_in_word_off + (j << step_sh) (fixed stride, same word)
//   advance: km_rd_off += tcN*elem_bytes;  dest_addr += one block (1 << calc_sh2)

Properties that keep it safe and small (~60 lines in VX_dxa_smem_wr.sv):

  • Alignment is structural: a line's element 0 is always n-block-aligned (rows and line boundaries are both tcN-aligned), so groups never straddle words; a partial tail group is masked by the remaining fill level through the existing fb_level accounting.
  • Guarded fallback: configs whose group span exceeds the SMEM word (e.g. FEDP2K, whose LG_FEDP_RATIO doubles the stride) take the original element-wise path unchanged — correctness never depends on the new mode. Extending grouping to FEDP2K (two words per group) is a follow-on.
  • Multicast unchanged: the replay machinery operates per emitted word and simply replays 4× fewer words — validated on sgemm_tcu_wg_dxa_mcast.
  • Model parity: the grouped profile (8 beats per B line) is exactly what simx already models, so the fix closes a model/RTL divergence rather than opening one.

4P2–P5 — the rest of the ranked plan

  1. bbuf plan-ahead prefetch (next wall). After P1, tbuf stalls are what remains between 74,947 and the ~65k the fast-DXA simx probes bound (both schedules flatten near 60k when the drain is free). Replace the single-outstanding demand fetch in VX_tcu_bbuf with a per-WGMMA tile plan streamed at N≥4 outstanding line fetches into full-tile residency (1 KB per core at this geometry — the simx tbuf's exact behavior). This also amortizes the barrier-forced refetch (cache hits are already 10,744/5,393-read ratio with slots; full-tile residency makes the refetch one burst, not per-uop round-trips).
  2. TCU-first DMA arbitration. The rejected-today experiment: land the 1-line index swap together with P2, where its measured 2.4× tbuf-stall reduction converts into cycles instead of barrier wait. Zero hardware cost.
  3. Fix the DXA perf counters. perf_gmem_reqs and the latency/span counter in the gmem_req/worker accumulate path report impossible values (F-rejected above). They cost this investigation real time and will cost the next one more.
  4. (Optional) DXA response staging. A 2-line response skid decouples the socket response bus from drain progress entirely; mostly subsumed by P1's 4× shorter holds.

5Where this lands the fork

With P1 alone, WGMMA+DXA is decisively the fastest sgemm on the RTL — the original "on paper it should be faster" claim now holds in hardware simulation, not just in the model. The remaining ~15k to the compute-plus-tbuf bound is P2/P3 territory; beyond that, the roofline arguments from the first report (multicast reuse, CTA/ISSUE_WIDTH decoupling) still stand for the order-of-magnitude horizon.

6Risks and review notes

  • Timing: the spread network is tcN bounded shifts plus an OR reduce inside the existing drain stage — comparable depth to the barrel shifter already there. If it pressures the clock, it pipelines cleanly one stage (the drain is throughput-bound, not latency-bound).
  • Coverage: validated on dense BlockMajor (grouped), FEDP2K (fallback), multicast (grouped), and the 32³/128³ sizes; K-major, Flat, and row-major paths are untouched by construction. Recommended before landing: the full dxa.yaml + tensor*.yaml catalog and a model_parity pass (expected to improve — RTL now matches the model's drain).
  • Perf-gate baselines: cycle counts drop ~36% on DXA workloads — the affected gates will trip as intended-improvement and need the human-run baseline regeneration after landing.
  • Counter semantics (P4) should land with or before P1 so the gate baselines are regenerated against honest counters.
